Engineering note · AnyDrag · 2026-07-27

当另一个 App 把你抹掉的 modifier flag 又贴了回去

AnyDrag 的 Ctrl + 左键拖动在 BetterMouse 运行时全面失效。真正的原因不在按键映射，而在 CGEvent tap chain 的执行顺序——以及一个只能在 gesture 开始那一刻才能赢下的竞争。

Issue#27 FixTrailingFlagScrubber.swift 环境macOS 26.x Status已验证

这份文档记录一次完整的排查：从错误的假设，到实测推翻它，再到最终的修复。核心机制（CGEvent tap 的分层与排序）对任何使用 event tap 的 macOS App 都适用——同一台机器上 HyperCapslock 的 Hyper 键也被 BetterMouse 打断，成因完全相同。

1 · 现象

用户报告：把 Control 设为 primary modifier 后，Ctrl + 左键拖不动窗口，按下去反而弹出 context menu。他自己在干净的虚拟机里定位到了 BetterMouse，并且——这一点后来被证明是关键线索——把 BetterMouse 里的功能逐个关掉，问题依旧。

AnyDrag 的窗口拖动不走 Accessibility API。它把 gesture 伪装成「按住 title bar」：拦截 mouse event，把坐标改写到目标窗口的 title bar 区域，让 window server 自己执行 native drag，全程零 per-frame IPC。这个伪装有一个前提——

前提

macOS 的 AppKit 会把 Control + leftMouseDown 在 NSResponder 层解释成 secondary click（等同右键）。所以 AnyDrag 必须从它合成的 title bar click 上抹掉 .maskControl，否则那一下点击会被当成右键，native drag 根本不会开始。

这段抹除逻辑早就存在，也一直有效。问题是：有人在下游把它撤销了。

2 · CGEvent tap 的排队机制

要理解冲突，先要理解 event 在被 App 收到之前经过了什么。CGEvent.tapCreate 有两个决定位置的参数：tap（tap location，事件管线的哪一段）和 place（tap placement，在这一段的队列里插哪儿）。

Figure 1. tap location 之间的先后是架构决定的；同一 location 内部则是一条可以被任意成员改写或截断的串行链路。冲突只可能发生在链路内部。

同一个 tap location 内部的排序由 place 决定，规则有两条，都经过实测确认（见 §6 的 ordertest）：

  • kCGHeadInsertEventTap（插到队首）——后创建的排在更前面，因为它被插到了队首。
  • kCGTailAppendEventTap（追加队尾）——后创建的排在更后面。
  • 所有 head-inserted 的 tap 一律排在所有 tail-appended 的 tap 前面。
Figure 2. 这条规则是整个修复的支点。「最后追加到队尾的 tap 拥有最终发言权」直接决定了修复方案必须在什么时机创建 tap。

还有一个容易踩的坑：CGGetEventTapList 返回的顺序不是执行顺序。实测中它把 HID 层的 tap 排在了 session 层之后，而 HID 层明明先执行——那个列表看起来是按创建时间倒序排的，不能用来判断谁先谁后。

3 · 排查过程，包括两次错误结论

如实记录走过的弯路，因为它们比结论更能说明该怎么排查这类问题。

错误结论一：「BetterMouse 把 Ctrl + 左键改写成了右键」

这是用户和我最初共同的假设，听起来完全合理。做法是在 HID 层和 session 链尾部各挂一个 listen-only tap，对比同一次手势在两处的样子。结果：整个 log 里没有出现过一个 rightMouseDown。没有任何 button 被改写。假设当场作废。

错误结论二：「是『左键点击穿透』这个功能干的」

实测数据显示，一次拖动里只有首尾两个事件的 flag 被改了，中间几百个 leftMouseDragged 完好无损。而 BetterMouse 那个管左键的 tap，监听范围恰好是 LDown, LUp 而不含 LDrag。据此我推断是 click-through 功能在「重新发出点击」时重置了 flag。

用户一句话推翻：那个开关本来就是关着的。猜功能是错的方法——应该直接测机制。

决定性的 controlled experiment

不再猜是哪个 feature，改为直接验证机制：自己插一个 head-inserted 的 modify tap 强行抹掉 Control，再在链尾观察它有没有被贴回来。唯一的变量是 BetterMouse 在不在运行。

// BetterMouse 运行中

[96.873] STRIP-IN  leftMouseUp   was=ctrl now=-    BM=running
[96.877]   CHAIN-END leftMouseUp   flags=ctrl    ← 被贴回来了

[108.704]   CHAIN-END leftMouseDown flags=-      ← 保持抹掉
[108.799] STRIP-IN  leftMouseUp   was=ctrl now=-   BM=QUIT
[108.800]   CHAIN-END leftMouseUp   flags=-      ← 保持抹掉
Root cause

BetterMouse 在处理 left mouse down / up 时，会按 physical modifier key 的当前状态重新盖一遍 event flags。用户手指还按着 Control，于是 AnyDrag 刚抹掉的 .maskControl 被原样贴回。它不处理 leftMouseDragged——这个不对称正是定位到它的线索。

后果链条完整闭合：AnyDrag 合成的 title bar click 带着 Control 抵达目标 App → AppKit 判定为 secondary click → 弹出 context menu，native drag 从未开始。

Figure 3. AnyDrag 的抹除并没有失败，它只是不是最后一手。链路上任何下游成员都能推翻上游的修改。

4 · 修复：为什么时机比位置更重要

既然「最后动手的说了算」，直觉方案就是：AnyDrag 再挂一个 tail-appended 的 tap，在事件离开 chain 之前把 Control 再抹一次。实测确实立刻见效——但这是运气。

tail-appended 的 tap 按创建顺序排列，所以「谁最后创建谁在最后」。那次实测里 BetterMouse 先启动、验证程序后启动，恰好赢了。把顺序倒过来——让用户重启一次 BetterMouse——修复立刻失效：

Figure 4. 一个在 App 启动时创建的 tail tap，其正确性取决于用户何时启动别的软件——这不是修复，是赌博。
修复的核心

tail append 的语义是「排到创建那一刻已存在的所有 tap 之后」。所以只要把收尾 tap 的创建推迟到 gesture 开始的那一刻，无论对方何时启动，它的 tap 都已经存在，我们必然排在它后面。竞争条件被时机消灭了。

实现就是 TrailingFlagScrubber：mouse down 触发 gesture 时 tail-append 一个 tap，gesture 结束就销毁。几个必要的细节：

  • 只抹按下那一刻真正持有的 flag。取 candidates ∩ event.flags，为空就完全不创建 tap——没装这类工具的用户零开销。
  • 等 gesture 自己的 release 事件穿过去再销毁。收尾 tap 位于整条链路的最下游，手一松就拆，会把仍带着 Control 的 leftMouseUp 直接交给 App。
  • 只有指定 type 的 release 才被继续处理。无拖动的中键点击、无拖动的右键 resize 会把 release 事件吞掉，它永远不会到达队尾；若不加限定，紧接着一次无关的 Ctrl + click 就会被误抹。
  • 三重兜底：watchdog timer、tap 被系统 disable 时自毁、stop() 时主动清理并阻止正在创建中的 tap 挂上来（否则会留下一个没人 service 的 tap，卡住整个鼠标输入直到系统超时）。
// gesture 开始：此刻 tail append，必然排在所有既存 tap 之后
guard let tap = CGEvent.tapCreate(
    tap: .cgSessionEventTap,
    place: .tailAppendEventTap,   // ← 关键
    options: .defaultTap,
    eventsOfInterest: mask,
    callback: trailingFlagScrubberCallback,
    userInfo: selfRef
) else { return }

// callback：gesture 进行中无条件抹；gesture 结束后只认自己的 release
if let terminator {
    guard type == terminator else { return passthrough }
    event.flags = event.flags.subtracting(flags)
    end()
}

5 · 给其他 App 作者

这个坑不是 AnyDrag 独有的。同一台机器上 HyperCapslock 的 Hyper 键在 BetterMouse 运行时同样失效——它也依赖对 modifier flags 的改写，也在 session 层，也会被下游重新盖章。判断你是否中招，只需要三个问题：

问题中招的信号
你的功能是否依赖「从 event 上移除某个 modifier flag」？ 是 → 高风险。下游任何一个按物理按键状态重新盖章的 tap 都能撤销它。
你的 tap 是不是 headInsertEventTap？ 是 → 你在最前面，意味着你的修改最容易被后面的人推翻。
症状是否只在某些 App 上出现？ 是 → 很可能 flag 确实传到了 App 层，只是各家 App 对它的反应不同。

通用的修法就是本文的方案：在 gesture / 生效窗口开始的那一刻 tail-append 一个短命的 tap，把同一套 flag 再抹一次，窗口结束就销毁。不要在 App 启动时创建它——那会输给任何一次对方的重启。

另一条值得记住的经验：不要猜是对方的哪个 feature 干的。本文两次错误结论都源于猜 feature。直接做 controlled experiment——自己插一个 tap 改点什么，在链尾观察它有没有被改回去，唯一变量是对方进程在不在——十分钟就能得到确定答案。

7 · 拆掉任何一块会怎样

去掉…症状严重度
place: .tailAppendEventTap 改成 head insert 就排到了 BetterMouse 前面，抹除依旧被撤销，修复完全无效 HIGH
gesture 开始时才创建（改为启动时创建一次） 用户重启一次 BetterMouse 就失效，且无任何提示——最隐蔽的失败模式 HIGH
shutdown() 的 acceptingNewTaps 闸门 stop() 与 gesture 创建 tap 撞车时，会留下一个没人 service 的 session tap，卡住鼠标输入直到系统超时 HIGH
只认指定 type 的 release（pendingTerminator） release 被吞掉的手势之后，下一个无关点击会被误抹 modifier，例如 Ctrl + click 不弹菜单 MEDIUM
watchdog timer 手势中途被打断（tap 被 disable、鼠标 up 丢失）会留下长期存活的 tap，持续影响无关输入 MEDIUM
candidates ∩ event.flags 的过滤 功能不受影响，但每次手势都会多创建一个 tap——没有冲突工具的用户白付开销 LOW

8 · 已知的剩余边界

如实记录一处没有覆盖的场景：如果 gesture 由 CapsLock hold（Hyper）触发、按下时并未持有 Control，而用户在按下之后、拖动之前才补按 Control，则收尾 tap 不会被创建，问题依旧。堵住它需要每次手势都无条件创建 tap，代价是牺牲「无冲突工具的用户零开销」。当前选择保留这个边界，因为它需要一个相当刻意的操作序列才能触发。
