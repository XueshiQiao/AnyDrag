What's New in 1.4.2

  • Fix: memory grew on every window drag and never came back down — AnyDrag's event tap was over-retaining each mouse event it processed, leaking one system event object per event. During a drag (dozens to hundreds of events per second) memory climbed steadily and never recovered — one report reached 500 MB. The events are now released correctly per the event-tap contract. (Thanks to @eunrui for the clear report in #9.)
  • Fix: memory spike during middle-button tile preview — While sliding to preview a tile target, the translucent preview overlay allocated a full-resolution bitmap the size of the previewed region — tens of MB per preview on high-resolution displays. The overlay is now GPU-composited, so it costs almost nothing regardless of the previewed area.

1.4.2 更新内容

  • 修复:每次拖动窗口内存都会增加且不回落 — AnyDrag 的事件 tap 在处理每个鼠标事件时多持有了一次引用,导致每经过一个系统事件就泄漏一个事件对象。拖动时鼠标事件每秒高达几十上百个,内存因此持续上涨且降不下来——有用户反馈涨到了 500 MB。现在事件会按照事件 tap 的约定被正确释放。(感谢 @eunrui 在 #9 提交清晰的反馈)
  • 修复:鼠标中键平铺预览时内存骤增 — 滑动预览平铺落点时,那个半透明预览框会按预览区域大小分配一整块全分辨率位图,在高分屏上每次预览要占用几十 MB。现在预览框改由 GPU 合成,无论预览区域多大占用都极小。

What's New in 1.4.0

  • Fix: Accessibility permission row stuck on "Granted" after revoke — In Settings → General, the Accessibility row continued to display "🟢 Granted" indefinitely after the permission was toggled off in System Settings. AnyDrag now correctly reflects the current permission state shortly after each toggle. (Thanks to @FisherRone for the careful reproduction and reporting in #7.)
  • Fix: revoking Accessibility could freeze every mouse click system-wide — The protection shipped in 1.3.0 regressed in 1.3.2: after a revoke, AnyDrag's recovery path was inadvertently resurrecting the unauthorized event tap instead of tearing it down, leaving it at the head of the system event chain swallowing every click. AnyDrag now detects the revoke reliably and removes the tap cleanly.
  • Fix: launch permission alert could be silently skipped — On macOS 14/15, AnyDrag's internal trust probe (a listen-only mouse event tap) would succeed even when Accessibility was actually denied, so the launch flow concluded "permissions OK" and never showed the request alert — the app appeared running but the event tap never started. The launch flow now uses the documented AXIsProcessTrusted() API as the single source of truth, so the alert appears when needed.
