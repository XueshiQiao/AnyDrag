Research note · AnyDrag · 2026-07-25

macOS Spaces：读得到，写不进

窗口属于哪个桌面，任何普通 App 都能免费、快速、无需关闭 SIP 地查出来；但把别人的窗口挪到另一个桌面，系统会静默拒绝。这条分界线决定了所有多桌面工具的形态。

测试机macOS 26.4.1 (25E253) · arm64 方法自写探测程序实跑 结论读 · 可用 写 · 不可用

本文所有结论都来自在上述机器上真实运行的探测程序，不是从文档或他人代码推断的。凡是没有实跑验证的推测，都在 §7 单独列出并标注。

1 · 结论先行：能力边界是一个 2×2

macOS 没有任何公开接口能告诉你"这个窗口在哪个桌面"。CGWindowListCopyWindowInfo 能列出全部窗口，但返回的字典里根本没有 Space 字段。所有做到这件事的 App，走的都是 SkyLight / CoreGraphics 的私有接口。

这些接口的能力不是"能用 / 不能用"这么简单，而是沿着两个维度切开的：

图 1. 唯一被堵死的是右下角这一格——而它恰好是做"多桌面管理工具"唯一真正需要的能力。三条不同的写入路径全部落在这一格里（§5）。

2 · 读：三条路，别人都在用哪条

路径谁在用拿到什么实测
读 com.apple.spaces 偏好文件 Amethyst 早期、spaces-renamer 每个 Space 的 UUID，外加一串 window id 可读但不实时
CGSCopyWindowsWithOptionsAndTags
按 Space 查窗口		 yabai、AltTab 一个 Space 里有哪些窗口 快，但会漏
CGSCopySpacesForWindows
按窗口查 Space		 Hammerspoon、Phoenix 一个窗口在哪些 Space 上 完整，推荐

偏好文件那条路是最老的做法（ianyh 在 2013 年前后写过），它读的是 WindowServer 落盘的快照，切换桌面后不会立刻更新，只适合做冷启动时的初始化。真正实时的只有后两条。

需要的符号声明

注意一个链接上的坑：CGS* 开头的符号由 CoreGraphics 导出，SLS* 开头的才在 SkyLight 里。两套是同一批函数的两个名字。只链 SkyLight 而不 import CoreGraphics，链接器会报 undefined symbol。

import CoreGraphics   // 必需：CGS* 符号从这里来

typealias CGSConnectionID = UInt32
typealias CGSSpaceID      = UInt64

@_silgen_name("CGSMainConnectionID")
func CGSMainConnectionID() -> CGSConnectionID

// 列出所有显示器上的所有 Space
@_silgen_name("CGSCopyManagedDisplaySpaces")
func CGSCopyManagedDisplaySpaces(_ cid: CGSConnectionID) -> CFArray

// 查某个窗口在哪些 Space 上。mask 0x7 = kCGSAllSpacesMask
@_silgen_name("CGSCopySpacesForWindows")
func CGSCopySpacesForWindows(_ cid: CGSConnectionID,
                             _ mask: Int,
                             _ wids: CFArray) -> CFArray

3 · 实测输出

探测程序在一台外接一块显示器、共 3 个桌面的 Mac 上跑出的真实结果：

== CGSMainConnectionID() -> 1708767
== CGWindowListCopyWindowInfo(.optionAll) -> 311 windows（公开接口里没有任何 space 信息）

Display #0  uuid=1F26ABAD-…  spaces=1    current -> 1
  Space id64=1    type=user  windows=25   <== 当前
    apps: Control Center×19, Window Server×2, AnyDrag, CCSwitcher, Dock, System Settings

Display #1  uuid=EF9F6A81-…  spaces=2    current -> 142
  Space id64=142  type=user  windows=29   <== 当前

  Space id64=148  type=user  windows=3

"每个桌面上有什么 App"这个需求，技术上完全成立，而且很便宜。全量扫描 300 多个窗口只要几毫秒，做成菜单栏常驻刷新毫无压力。

4 · 四个只有真跑才知道的坑

坑 1：批量调用返回的不是一一对应的结果

这是最容易写出静默错误的地方。CGSCopySpacesForWindows 接受一个窗口数组，直觉上应该返回一个等长的数组，下标对下标。实际上它返回的是去重后的集合。

图 2. 这个 API 不会报错，也不会崩溃——它只是返回了一个语义完全不同的数组。逐窗口调用单次只要 0.012 ms，调 300 次也才 4 ms，没有理由为了"优化"去批量传。

坑 2：按 Space 查的那条路会漏掉最小化的窗口

同一时刻用两种方法查同一批 Space，结果并不一致：按 Space 查（方法 A）拿到的窗口集合，始终是按窗口查（方法 B）的真子集。差额全部是最小化 / 隐藏的窗口。

图 3. 方法 A 快 50 倍（3 次调用 0.3 ms vs 306 次调用 15 ms），但它只看得见"已经被渲染出来"的窗口。做桌面总览必须用方法 B，否则用户最小化一个窗口，它就从总览里消失了。

坑 3：大部分窗口根本不属于任何 Space

公开接口报告 304 个窗口，其中只有 91 个能查到 Space，剩下 213 个查出来是空数组。这 213 个是 WindowServer 内部窗口（94 个）、输入法候选框、菜单、阴影层之类的东西。

必须按 kCGWindowLayer == 0 过滤，否则一个桌面会显示成"有 19 个 Control Center 窗口"。

坑 4：Space 的数字 id 会变，UUID 才是稳定标识

这个坑是意外撞见的。两次探测间隔约 20 分钟，同一个桌面的 id64 从 142 变成了 193，而它的 UUID 一个字符都没变。

图 4. 任何要落盘的数据——桌面名字、图标、每桌面的时间统计——都必须以 UUID 为键。用 id64 做键，用户开关一次全屏 App，配置就会错位到别的桌面上。

顺带确认：macOS 自己不存桌面名字。CGSSpaceCopyName 返回的就是那串 UUID，不是人类可读的名字。所以 SpaceJump 那类 App 的"给桌面起名"功能，是自己维护了一张 UUID → 名字的映射表。

5 · 写：三条路径，全部静默失效

符号是齐的。用 dlsym 逐个查，写入相关的十几个私有符号在 macOS 26.4.1 上一个不少：CGSMoveWindowsToManagedSpace、CGSAddWindowsToSpaces、CGSRemoveWindowsFromSpaces、CGSSpaceCreate、CGSSpaceDestroy、CGSManagedDisplaySetCurrentSpace 全部 EXISTS。

但符号存在 ≠ 能用

实测方式：起一个全新的 TextEdit（一个真正的外部进程），拿到它的 window id，依次用三条不同的写入路径尝试把它挪到另一个桌面，每次都用 CGSCopySpacesForWindows 回读验证。

写入路径返回回读结果
CGSMoveWindowsToManagedSpace void，无错误 NO-OP 窗口没动
CGSAddWindowsToSpaces void，无错误 NO-OP 窗口没动
CGSSpaceSetCompatID + CGSSetWindowListWorkspace
yabai 的老路径		 1006 = kCGErrorNotImplemented NO-OP 窗口没动
对照组：同样的调用，作用在自己进程的窗口上 — CGSMoveWindowsToManagedSpace 把自己的窗口从 space 1 挪到 142，回读确认 成功

注意第三条返回的是 kCGErrorNotImplemented——Apple 把这个函数明确地做成了空实现。前两条更"礼貌"：不返回任何错误，安安静静地什么也不做。

这解释了 yabai 为什么必须关 SIP

yabai 要移动窗口 / 创建销毁桌面，走的不是"直接调这些函数"，而是往 Dock.app 里注入一个 scripting addition，从 Dock 的进程里去调。因为 Dock 才是持有 Space 管理权限的那个进程。注入需要关闭 SIP，这是它那个恶名昭著的安装步骤的全部原因。

而 AeroSpace 选择了另一条路：完全不碰系统 Spaces，自己造一套虚拟工作区，切换时把不属于当前工作区的窗口挪到屏幕外面去。这样就绕开了整堵墙，代价是它管理的"工作区"和 Mission Control 里看到的"桌面"是两套互不相干的东西。

6 · 对 AnyDrag 意味着什么

能力可行性说明
桌面总览：每个桌面上有哪些 App 可做 几毫秒扫全量，无需关 SIP。用方法 B + layer 过滤 + UUID 做键。
菜单栏显示"当前在第几个桌面" 可做 CGSManagedDisplayGetCurrentSpace，支持多显示器分别取。
给桌面起名字 可做 系统不存名字，得自己维护 UUID → 名字表。
用 API 把窗口挪到别的桌面 做不到 三条路径全部静默失效，除非关 SIP 往 Dock 注入。
用模拟拖拽把窗口挪到别的桌面 未验证 见下。这是 AnyDrag 唯一有优势的角度。
还没走完的那条路

macOS 原生就支持"拖着窗口撞到屏幕边缘停一下 → 窗口跟着换到下一个桌面"。这是用户级的交互，不受私有接口的限制。AnyDrag 本来就在窗口服务器层面合成原生的标题栏拖拽，理论上有条件把这套动作自动化成一个快捷键或菜单项。这条路我没有实测过，但它是唯一一条不需要关 SIP 又能真正移动窗口的路径，值得单独验一次。

7 · 明确没有验证的部分

  • 是否真的零权限。探测程序运行时没有弹出任何权限对话框，但它是从一个已经被授予辅助功能权限的终端里启动的，子进程可能继承了归属。要确认"独立 App 零权限可用"，得打包成 .app 单独跑一次。
  • SpaceJump / Swish 的"拖窗口到别的桌面"具体怎么实现。基于本文的结论，它们只可能走模拟用户操作那条路，但我没有反编译验证过。
  • CGSAddWindowsToSpaces 作用在自己窗口上是否有效。对照实验设计有误——目标 Space 恰好就是该窗口已在的 Space，所以这一格结论无效。只有 CGSMoveWindowsToManagedSpace 的自窗口移动是确实验证过的。
  • CGSSpaceSetCompatID 的返回值。实测返回 1112379，不是任何已知的 CGError。两次调用返回同一个值，推测这个函数实际返回 void，我把它声明成返回 CGError 导致读到了寄存器里的残留值。这个返回值不应被当作错误码解读。
  • 更早 / 更晚的 macOS 版本。全部结论只在 macOS 26.4.1 (25E253) arm64 上成立。这些是私有接口，Apple 随时可能改。
