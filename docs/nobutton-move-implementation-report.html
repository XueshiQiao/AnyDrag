按住修饰键移动鼠标即可移动窗口

一份关于「无键移动窗口」实现方案的完整拆解,并与既有的「修饰键 + 左键拖拽」实现逐项对比——它们共用同一套窗口服务器原生拖拽引擎,真正的差异只在「那只被按住的左键从哪来」。

1 · 背景:两个特性,同一条铁律

AnyDrag 的全部价值,建立在一条铁律上:绝不使用 Accessibility(AX)逐帧设置窗口位置。AX 每帧 5–10ms 的 IPC 延迟正是这个项目存在的理由。两个「移动窗口」特性都必须绕开它。

它们采用同一个技巧:不去「移动」窗口,而是改写鼠标事件的坐标,骗过窗口服务器(WindowServer),让它以为用户正在拖拽标题栏。于是窗口由窗口服务器在合成器层面原生移动,每帧零 IPC,顺滑程度与手动拖标题栏完全一致。

  • 实现一(既有):修饰键 + 按住左键拖拽 → 移动窗口。用户的真实左键提供了「被按住」的状态。
  • 实现二(本次原型):修饰键 + 移动鼠标(不按任何键)→ 移动窗口。没有真实按键,AnyDrag 必须把整只左键完全合成出来。
一句话总结

两套实现共用同一个坐标改写引擎(TitleBarDragStrategy)。实现一里,那只「按住的左键」是用户真按下的;实现二里,它是 AnyDrag 凭空合成、再凭空收尾的。几乎所有差异都从这一点派生出来。

2 · 共享的底层:伪造一次标题栏拖拽

两套实现最终都汇入 TitleBarDragStrategy。它的工作分四步,关键在于把首个事件「延后一拍」转成落在标题栏上的合成 leftMouseDown,之后所有事件只做一个固定的 Y 轴偏移。

图 1. 这套四步流程是两个特性共用的引擎。它们的区别只在于「起始事件」「后续事件」「收尾事件」分别是什么类型、以及由谁产生。

坐标改写的核心只有几行——把任意来源的事件,改写成窗口服务器眼中合法的标题栏拖拽:

// TitleBarDragStrategy.handleMouseDragged —— 两套实现都走这里
if needsInitialMouseDown {              // 第一个后续事件 = 合成按下
    needsInitialMouseDown = false
    event.type = .leftMouseDown
    event.location = dragPoint            // 标题栏锚点
    return Unmanaged.passUnretained(event)
}
event.type = .leftMouseDragged
let pos = event.location
event.location = CGPoint(x: pos.x, y: pos.y + yOffset)   // 仅平移 Y
return Unmanaged.passUnretained(event)

两者还共享一组细节:都剥掉 Control 标志位(否则 Control+leftMouseDown 会被 AppKit 当成右键);都先做修饰键匹配、光标下找窗口、放行主屏菜单栏、AX 授权守卫;都把首个事件 suppress 掉以便先激活并抬升目标窗口。

3 · 实现一:修饰键 + 左键拖拽

这是 AnyDrag 的原始能力。触发器是按住主修饰键时的 leftMouseDown(matchesConfiguredModifier,还额外允许叠加 Option,以兼容 macOS 自带的「按住 Option 拖拽分屏」)。

关键点:整个手势的「按键按住」状态由用户的真实左键提供。窗口服务器需要一只「按下的左键」才会持续移动窗口——这里它本来就有。AnyDrag 只负责改写坐标:

  • leftMouseDown(真) → 吞掉,激活/抬升窗口,needsInitialMouseDown = true。
  • leftMouseDragged(真)→ 第一个转成标题栏 leftMouseDown,其余做 Y 偏移。
  • leftMouseUp(真)→ 同偏移收尾,手势自然结束。

手势的「开始」和「结束」边界天然由真实按键的按下 / 抬起划定,无需额外侦测。双击则触发最大化/还原;中键是同一引擎的变体(把 otherMouse* 用 rewriteToLeftButton 改写成 left*)。

4 · 实现二:修饰键 + 移动鼠标(无键移动)

新原型要在没有任何真实按键的情况下,做出同样的原生标题栏拖拽。窗口服务器仍然只在「有按键按住」时移动窗口——所以 AnyDrag 必须把这只左键从头合成到尾:开头用「改写事件」按下它,结尾用「投递事件」松开它。

新增监听与触发器

事件 tap 在原有的九种按键事件之外,新增监听 .mouseMoved 与 .flagsChanged。触发器是专用修饰键(matchesNoButtonModifier,精确匹配、不做 Option 叠加、不含 Hyper),与主修饰键完全分开;空 = 关闭,默认关,所以不开启时零影响。

四个阶段:idle → armed → dragging → 收尾

图 2. 无键移动需要一个显式的状态机,因为它没有真实按键的「按下 / 抬起」作为天然边界。armed → dragging 的延后一拍,对应图 1 里「延后合成按下」那一步。

「武装」与「接管」的核心代码——注意首个移动只激活窗口、不立即合成按下:

// handleMouseMoved —— idle 分支:武装
guard matchesNoButtonModifier(event.flags) else { return passthrough }
let yOffset = windowTop + noButtonStrategy.titleBarYOffset - screenPoint.y
state.noButtonPhase = .armed
return noButtonStrategy.handleMouseDown(..., rewriteToLeftButton: true)  // 吞掉

// 下一个 mouseMoved —— armed → dragging:合成按下,之后持续跟随
if state.noButtonPhase == .armed { state.noButtonPhase = .dragging }
return noButtonStrategy.handleMouseDragged(event: event)

5 · 逐项对比:相同与不同

把两套实现并排看,会发现它们的「相同」远多于「不同」——区别高度集中在「那只左键的来源与生命周期」。

图 3. 两条完全不同的输入事件流,经过同一个引擎改写后,在窗口服务器眼里归一为同一串左键拖拽事件。实现一的事件本就是 left*(只改坐标);实现二要把 mouseMoved「变身」成 left*,并自己补上收尾的 leftUp。

相同之处

  • 同一个坐标引擎:都用 TitleBarDragStrategy 的 dragPoint / yOffset / 标题栏锚点。
  • 同一个「延后一拍」:都吞掉首个事件、先激活抬升窗口,把合成 leftMouseDown 推迟到下一个事件,留 ~8ms 给窗口重排。
  • 同一个结果:窗口服务器原生移动,每帧零 IPC,1:1 跟随光标。
  • 同一组守卫:剥 Control 标志、修饰键匹配、光标下找窗口、放行菜单栏、AX 授权检查。
  • 都不碰 AX 逐帧定位。

不同之处

6 · 无键移动独有的难点

「完全合成一只左键」带来了三个实现一根本不会遇到的问题。

难点 A:没有天然的结束事件

「无键」的字面意思是整个手势不按任何鼠标键:用户只按住修饰键并移动鼠标。所以根本没有鼠标键可松开——不存在 leftMouseUp 这样的天然结束信号。手势的边界由修饰键划定:按住即开始,松开即结束。

而「松开修饰键」产生的是 flagsChanged(键盘修饰键变化),不是鼠标事件;只监听鼠标事件就永远看不到它。退一步说,即便只盯着 mouseMoved 也不行:用户在光标静止时松开修饰键连 mouseMoved 都不会产生,窗口会一直黏在光标上。所以必须监听 flagsChanged。对比之下,左键拖拽全程按住真实左键,松开它就是天然的 leftMouseUp 结束信号——这正是两者最根本的差异之一。

难点 B:HID 注入会「吞掉」真实的松手(本次最棘手的 Bug)

原本的收尾方式是:在 .cghidEventTap(HID 层)投递一个合成 leftMouseUp。在纯无键场景下没问题。但只要用户在移动途中真的按了一下左键,物理左键此刻是按下状态;此时在 HID 层注入一个 leftMouseUp,会打乱按键状态、吞掉用户随后真实的松手事件,导致窗口服务器的左键卡在「按住」——表现为:移动卡死(再次按修饰键移动无效),以及松手后窗口突然「跳到标题栏贴着光标」。

这个根因不是猜的——是加日志、真机复现、读日志定位的:复现里那个真实的 leftMouseUp 在日志中消失了,而 mouseMoved 却照常出现(证明物理键已松开),坐实了「松手被吞」。

图 4. 卡死与跳变是同一个根因的两种表现:合成左键被卡住没有被干净地收尾。修一个症状(跳变)而不动根因,只会让另一个(卡死)继续存在。

解法:让真实按键「协同」而非「对抗」合成拖拽

最终方案(经真机确认手感顺滑)是:移动进行中,真实鼠标按键一律无效化(inert)——它们永远不会到达窗口服务器。

  • 按下真实左键 → 吞掉,不结束移动;记下「物理左键按下」。
  • 按住左键继续移动 → 用这些 leftMouseDragged 驱动同一个合成拖拽(同样做 Y 偏移)→ 窗口持续跟随,不卡顿、不跳变。
  • 移动只在松开修饰键时结束。
  • 绝不在物理左键按下时做 HID 注入:若在按键仍按下时松开了修饰键,则延后结束(pendingEnd),由随后那次真实 leftMouseUp 本身(改写到标题栏偏移)来干净收尾。
关键洞察

实现一从不需要处理「真实按键 vs 合成左键」的冲突,因为它的手势就是那只真实按键。实现二把整只左键合成出来,于是必须主动让真实按键退让——要么不发生(吞掉),要么去驱动同一个拖拽,但绝不能和合成事件抢同一只物理左键。

难点 C:常驻 mouseMoved 的开销(原型尚未严格门控)

mouseMoved 是高频事件。原型现状:tap 的 mask 始终包含它,只有当专用修饰键未配置(特性关闭)时,handleMouseMoved 第一行才廉价返回。这意味着——只要特性开启,哪怕修饰键此刻并未被按住,每个 mouseMoved 仍会进入回调并取一次锁。这是必须消除的开销。

正式版的正确做法不是「按特性是否开启」来门控,而是「按修饰键此刻是否被按住」来门控,且门控条件要尽可能苛刻。由于 CGEvent tap 的 mask 创建后不可改,正确实现是一个独立的、默认禁用的 mouseMoved 专用 tap,用 CGEventTapEnable 在运行时开关:

  • 主 tap(始终):按键事件 + flagsChanged(低频,常驻几乎零成本)。
  • 第二个 tap:只监听 mouseMoved,默认 disabled。
  • 在 flagsChanged 里:专用组合变为按住 → enable 第二个 tap;变为松开 → disable。

禁用状态下,系统根本不会把 mouseMoved 投递给它——回调都不触发,这才是真正的零成本(比「收到后廉价短路」彻底)。启用条件严格:仅当「专用修饰键非空 且 该组合此刻被按住」时才开。

7 · 失效分析:抽掉每一块会怎样

抽掉…症状严重度
.flagsChanged 监听 光标静止时松开修饰键无法结束 → 窗口黏在光标上 高
「延后一拍再合成按下」 窗口尚未重排到前台,合成的标题栏点击落空 → 拖不动 高
「物理键按下时不做 HID 注入」 真实松手被吞 → 窗口服务器左键卡死(移动卡死 + 松手跳变) 高
「按键无效化」协同 真实左键与合成左键抢同一物理按键 → 状态错乱 高
收尾 leftMouseUp 的坐标偏移(用 raw 坐标) 结束瞬间窗口跳到「标题栏贴光标」 中
独立的专用修饰键(改用主修饰键) 按住主键还没点左键就动 → 抢走「左键拖拽」手势 中
剥离 Control 标志位 Control+合成 leftDown 被当成右键 → 拖拽失效 中
专用修饰键为空时的快速短路 关闭特性时每次 mouseMoved 仍走完整路径 → 额外开销 低

8 · 小结

「按住修饰键移动鼠标即可移动窗口」不是一个新机制,而是把既有「左键拖拽」所依赖的同一套窗口服务器原生拖拽引擎,接到了一个不带按键的触发器上。它们共享坐标改写、延后合成、零 IPC 跟随与全部安全守卫。

真正全新的工作量,都集中在「那只左键完全由软件合成」所派生出的三件事:用 flagsChanged 补出结束边界;让真实按键与合成左键协同而非对抗(按键无效化 + 绝不在物理键按下时做 HID 注入);以及常驻 mouseMoved 的性能权衡。原型已真机验证手感顺滑,正式化前的关键收尾是把 mouseMoved 改成按修饰键是否被按住来严格门控的独立可开关 tap(见 §6 难点 C)——修饰键没被按住时,绝不监听这个高频事件。
